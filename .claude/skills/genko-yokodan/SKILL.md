# 原稿横断タスクの進め方

## 規模

| | |
|---|---|
| 原稿 | `1.md` 〜 `10.md`（ファイル名＝巻数） |
| 話数 | 410話（`## 第N話　タイトル` が1話、`# 章名` が章） |
| 分量 | 73,086行 / 1,562,576文字 ≒ **156万トークン** |
| 1話あたり | 平均 178行 / 3,800字 ≒ 4千トークン |

全文は1Mウィンドウにも入らない。かといって、意味的なタスクは全部読まないと答えが出ない。
この矛盾の解き方が本スキルの中身。

**答え: 全部読むのは1回だけにする。**
意味を保ったまま1/6に圧縮した恒久索引を作り、以降のタスクは索引を起点に回す。

## 知識は二層で溜める

```
_yokodan/
  knowledge/            ★恒久知識・タスク非依存・永久に使い回す★
    digest.jsonl          話ダイジェスト 410行（約25万字。1Mウィンドウに収まる）
    digest/agent-*.jsonl  その断片（構築中の再開用）
    base.md               作品の基本設定。走査エージェント全員に配る前提知識
    chars.md              人物台帳（正体・呼称の変遷・一人称）
    timeline.md           年表
    glossary.md           用語・造語・スキル名
  tasks/<task>/         タスク知識・近い問いには再利用できる
    rubric.md             ものさし（実例引用つき）
    obs/agent-*.jsonl     生の観測 ★捨てない★
    report.md             最終成果
```

**生の観測を残すのが効く。** 「好感度じゃなく信頼度で」「部単位じゃなく巻単位で」
と言われたとき、観測が残っていれば**原稿を読み直さずに**統合だけやり直せる。

## 最初にやること

```bash
python .claude/skills/genko-yokodan/scripts/idx.py status
```

- **索引が無い / 欠けている** → 作る。→ `reference/digest.md`
  - 45エージェント / 入力156万トークンの一度きりの投資。**着手前にユーザーへ見積りを出して承認を取る**
  - 途中で中断しても `status` の欠番から再開できる
- **索引がある** → 下のタスク型に応じて進む

索引作りが今回のタスクとどちらが先か迷ったら、ユーザーに聞く。
ただし2回目以降のタスクがあり得るなら、索引を作ってからやる方がほぼ常に安い。

## タスクの型を見極める

### 型1: 意味的タスク（判断が要る）

「好感度の変遷」「性格の変化」「テーマの扱われ方」「作風の変化」「伏線の回収状況」など、
**正解が本文に書いていない**もの。→ **`reference/rubric.md` を読んでから進む。**

核心だけ先に:

> **map（走査）に採点させるな。観測させろ。採点は reduce でやれ。**
> 45人に「0-10で付けて」と言うと45通りのものさしが返り、変化のグラフが引けなくなる。
> エージェントには**事実と、方向(+/-/0)と強さ(強/中/弱)だけ**返させ、
> 数値は親が全観測を時系列に並べてから一気に振る。

進め方は R0 ものさし作り → R1 全走査 → R1.5 すり合わせ → R2 追い込み → R3 統合の5ラウンド。
エージェント間のやりとりは**親を経由した黒板方式**で行う（詳細は `rubric.md`）。

### 型2: 決定的タスク（数え上げ・列挙）

「全キャラの一人称」「地名を全部」「この語の初出」など、
**語として grep でき、判断より網羅が主**なもの。走査エージェントを回す前にスクリプトを試す。

```bash
# 候補の母集団を機械的に作る（0トークン。カタカナ語なら人名・地名がほぼ全部拾える）
python .claude/skills/genko-yokodan/scripts/vocab.py kata --min 15 --vols 2 --stop

# 対象がN個あるとき、それを最小の話数でカバーする話を選ぶ
python .claude/skills/genko-yokodan/scripts/cover.py --file targets.txt --per 2
#  実測: 13キャラを11話（全文の3.1%）でカバー

# 該当箇所だけ文脈つきで抜く
python .claude/skills/genko-yokodan/scripts/ctx.py ユズ --count       # 分布
python .claude/skills/genko-yokodan/scripts/ctx.py ユズ -B2 -A2 --max 30
```

**ただしスクリプトで完結すると思い込まないこと。**
「一人称」ですら、正体判明で一人称が変わるキャラがいれば意味的タスクに変わる。
機械抽出はあくまで**母集団を作る工程**であって、判断は必ずLLMがやる。

### 型3: 混合（実際はこれが多い）

意味的だが、対象を語で絞り込める場合。**最も安く、最も精度が高い段取り**:

1. `idx.py timeline` / `view` で索引から骨格と**転換点候補**を出す（安い）
2. `idx.py holes` で索引の取りこぼし候補を出す
3. **転換点候補と holes の話だけ**原文精読（全文の10〜20%）
4. それでも観測が空白の区間が残ったら、その区間だけ全走査

変化の分析では**転換点にトークンを集中投下するのが常に正しい。**
いきなり45エージェント投げるより安くて精度も高い。

## エージェント運用の掟（全タスク共通）

1. **本文を親コンテキストに入れない。**
   本文を読むのはエージェント。親が受け取るのは構造化結果とファイルパスだけ。
   親が本文で埋まると、以降の**全ターン**にその分の課金が乗り続ける。
2. **エージェントの返答に本文・要約そのものを含めさせない。**
   返させるのは「書いたパス / 件数 / 判断に迷った点3件まで」。
   迷った点が次ラウンドの論点になる（＝情報のやりとりの実体）。
3. **必ずディスクに書かせ、必ず再開可能にする。**
   投げる前に既存の成果物を見て、済んでいる範囲はスキップ。
4. **`Read` は必ず `offset`/`limit` 付き。** `Read("5.md")` は13万字。事故になる。
5. **前提知識を配る。** `knowledge/base.md` をエージェントのプロンプトに貼る。
   正体・伏線・呼称の変化は、その話だけ読んでいるエージェントには絶対に分からない。
6. **並列度は10前後まで。** 45エージェントを一度に投げず、波に分ける。
7. **モデルの使い分け**

   | 用途 | モデル | 理由 |
   |---|---|---|
   | 索引構築 | `sonnet` | 永続資産。品質が以後ずっと効く。Haikuだと関係性の機微を落とす |
   | 意味的タスクの観測 | `sonnet` | 誤読が結論を壊す |
   | 決定的な抽出・列挙 | `haiku` | 機械的作業。ここで節約が効く |
   | ものさし作り・統合 | 親（メインモデル） | 全体を見る工程だけは値切らない |

8. **取りこぼしを自覚して報告する。**
   サンプリングしたら「全ヒット何件中何件を見たか」を結論にも書く。スクリプトはこの数字を出す。

## スクリプト一覧

`.claude/skills/genko-yokodan/scripts/` 配下。リポジトリルートから実行。`--help` に使用例あり。
出力はUTF-8固定（Windowsコンソールの文字化け対策済み）。

| | 用途 |
|---|---|
| `idx.py` | 索引の `status` / `plan` / `merge` と、`view` `timeline` `holes` による絞り込み |
| `manifest.py` | 話の棚卸し。`--summary` 規模 / `--batch N` 行レンジ割り |
| `vocab.py` | 候補語の機械抽出。`kata` / `kanji` / `ruby` / `word` / `serifu` |
| `ctx.py` | 該当箇所の文脈つき抽出。`--count` 分布 / `--near` 共起 / `--regex` |
| `cover.py` | 複数対象を最小話数でカバーする話の選定（貪欲法） |

共通仕様:
- ルビ `《》` と `｜` は既定で除去してから照合（`｜追加データ《パッチ》` 記法があるため）
- `ctx.py --max` のサンプリングは既定で**全10巻に均等分散**。1巻だけ見て結論を出す事故を防ぐ

## 詳細ドキュメント

- `reference/digest.md` … 索引のスキーマ、構築手順、エージェント指示テンプレート
- `reference/rubric.md` … 意味的タスクの5ラウンド手順、ものさしの作り方、やりとりの3型

## やってはいけないこと

- ❌ **走査エージェントに0-10の数値を直接付けさせる。** ものさしがバラバラになり変化が読めなくなる
- ❌ **好意的な証拠だけ集める。** 反証（`dir: "-"`）を明示的に探させないと、必ず単調増加のグラフが出る
- ❌ **観測の無い区間を前後から補間して数字を作る。** 「観測なし」と書く
- ❌ **索引だけで意味的な結論を出す。** 索引は圧縮＝取りこぼしがある。`holes` を必ず確認し原文に戻る
- ❌ `Read("5.md")` のようにファイル全体を読む
- ❌ サブエージェントに本文をそのまま返させる
- ❌ 1巻だけ読んで「全巻でこうです」と結論づける。10巻は連載5年、作風も関係性も変わる
- ❌ `person.md` や Scrapbox の設定資料を根拠にする。README の通り**マスターは本文**。
  CLAUDE.md の「情報は常に本文から拾え」に従う。設定資料は仮説の種にはしてよい
- ❌ 中間結果をディスクに書かずに進める
