# 意味的タスクの進め方 ― ものさしと観測の分離

「ルナのタイヨウに対する好感度を0-10で部単位に」のような、
**正解が本文に書いていない**タスクをどう扱うか。

## 中心にある考え方

**map（走査）に採点させてはいけない。観測させろ。採点は reduce でやれ。**

45人のエージェントに「好感度を0-10で付けて」と言うと、45人ぶんの別々のものさしが返ってくる。
第3話の「7」と第300話の「7」に何の関係も無くなり、変化のグラフが引けない。

- **観測（map向き）**: 局所的に、その場面だけ見れば確定すること。
  「ルナがタイヨウに『信じてる』と言った(5.md:1234)」「タイヨウを避けた(3.md:800)」
- **評価（reduce向き）**: 全体を並べて初めて決まること。
  「部3の平均は6」「部5で一度下がってから急上昇」

エージェントには**事実と、強/中/弱と方向（+/-/0）だけ**を返させる。
0-10の数値は、親が全観測を時系列に並べてから一気に振る。

## 手順（5ラウンド）

### R0: ものさしを作る（親／小コスト・最重要）

**想像で基準を書かない。実際の本文から錨を拾ってから書く。**

1. 索引 (`idx.py timeline --pair A,B`) で対象の全体像を掴む
2. **極値と中間の実例**を原文で数箇所だけ読む（`ctx.py` か `idx.py view` の line から `Read`）
   - 最も冷たい場面、最も近い場面、中間らしき場面
3. その実例を引用しながら基準を書く

```
好感度スケール（ルナ→タイヨウ）
 0-1  敵意/無関心。例: 1.md:1780 初対面、名も聞かず立ち去る
 2-3  警戒。利害でのみ関わる。例: 1.md:3750 同行するが情報を渡さない
 4-5  同僚。信頼はあるが私情は無い。例: <本文引用>
 6-7  依存。私的な弱みを見せる。例: <本文引用>
 8-9  恋愛感情の自覚と表明。例: <本文引用>
 10   自己より優先。例: <本文引用>
```

**引用の無い段階があるなら、その段階は本文に存在しないかもしれない。**
その旨を最終報告に書く（無理に0-10を埋めない）。

4. あわせて**観測スキーマ**を決める（下記）

### R1: 全走査 map（45エージェント）

`idx.py plan` の割り当てをそのまま使う。各エージェントに渡すもの：

- タスクの説明（何を知りたいのか。採点基準そのものは**渡さない**）
- 観測スキーマ
- `_yokodan/knowledge/base.md`（正体・伏線・呼称の前提。これが無いと誤読する）
- 担当行レンジ

返させるもの：

- `_yokodan/tasks/<task>/obs/agent-<N>.jsonl` に観測を書く
- 親への返答は「件数 / 判断に迷った点 3件まで」だけ

観測スキーマの例（好感度タスク）:

```json
{"id": 123, "line": 4550, "who": "ルナ", "toward": "タイヨウ",
 "kind": "行動|発言|内心|呼称|身体距離|第三者評",
 "dir": "+|-|0", "strength": "強|中|弱",
 "fact": "本文にそう書いてある事実だけ。20〜60字",
 "quote": "根拠になる短い引用",
 "doubt": "解釈に迷ったなら書く"}
```

**必ず守らせる4点**

1. `fact` は解釈でなく事実。「好感度が上がった」は禁止、「手を握った」は可
2. `dir: "-"` の観測を意識的に探させる。**上がる証拠だけ集めると必ず単調増加になる**
3. 判断できないものは捨てず `dir: "0"` + `doubt` 付きで残す
4. `line` 必須。戻れない観測は使えない

### R1.5: すり合わせ（親）

観測JSONL（数百〜数千行。本文ではないので親に入れてよい）を全部読んで：

- `doubt` を集約 → ものさしの穴が見える → **ものさし v2** を作る
- 用語の揺れを統一（同一人物の別呼称、同じ現象の別ラベル）
- 観測が薄い区間を特定 → `idx.py holes` と突き合わせる
- 矛盾する観測のペアを列挙 → R2 の宿題にする

**ここが「情報のやりとり」の実体。** エージェント同士を直接しゃべらせるのではなく、
親が黒板を更新して次ラウンドで全員に配る。同期コストが無く、文脈も汚れない。

### R2: 追い込み（的を絞った再走査）

全走査ではない。R1.5 で出た宿題の箇所だけ。典型的には：

- 観測が薄いのに重要そうな区間 → その話を原文精読させる
- 矛盾ペア → 両方の原文を1エージェントに同時に読ませて裁定させる
- 転換点候補 → 前後を厚く読ませる（変化の分析では**転換点の精度が全て**）

### R3: 統合・採点（親／メインモデル）

観測を時系列（話id順）に並べ、ものさし v2 を当てて部単位のスコアを決める。

- 各スコアに**根拠となる観測を最低2件、`file:line` 付き**で添える
- 部の中で大きく動いたなら、部単位の1値に潰さず「部5: 4→8（転換点は 5.md:7633）」と書く
- **観測が無い部は「観測なし」と書く。** 前後から補間して数字を作らない
- 反証（`dir: "-"`）を無視して滑らかな曲線にしない。ギザギザなら、ギザギザが答え

### 保存

```
_yokodan/tasks/<task>/
  rubric.md        ものさし v1 / v2（実例引用つき）
  obs/agent-*.jsonl  生の観測。★これが資産★
  report.md        最終成果
```

**生の観測を捨てないこと。**
「好感度じゃなく信頼度で採点し直して」「部単位じゃなく巻単位で」と言われたとき、
観測が残っていれば**原稿を読み直さずに** R3 だけやり直せる。
索引と違って観測はタスク固有だが、近い問いには丸ごと再利用できる。

## 索引があるとき、全走査は本当に必要か

意味的タスクでも、まず索引で足りるか試す。判断基準：

| | 索引で足りる | 全走査が要る |
|---|---|---|
| 問いの軸 | 索引のフィールドに載っている（人物・関係・出来事・場所） | 載っていない（文体、比喩、笑いの質、テンポ） |
| 必要な粒度 | 話単位 | 文単位・場面単位 |
| 網羅性 | 代表例が挙がれば足りる | 数え上げる必要がある |

好感度タスクは**中間**。`idx.py timeline --pair ルナ,タイヨウ` で骨格は出るが、
索引は圧縮なので機微を落としている。現実的な最適解は：

1. `timeline` で骨格と転換点候補を掴む（安い）
2. `holes` で取りこぼし候補を出す
3. **転換点候補とholesの話だけ**原文精読（全文の10〜20%）
4. それでも部単位で観測ゼロの区間が残るなら、その区間だけ全走査

いきなり45エージェント投げるより、この段取りの方が安くて精度も高い。
**転換点にトークンを集中投下するのが、変化の分析では常に正しい。**

## エージェント間のやりとり ― 3つの型

| 型 | 使うとき | 実装 |
|---|---|---|
| **黒板型**（既定） | ほぼ全部 | 親が観測を集約 → 共有メモ更新 → 次ラウンドで全員に配る |
| **逐次リレー型** | 前の状態を知らないと解釈できない場合のみ | 部単位で直列。各部の担当が「部終了時点の状態」を書き、次の部の担当がそれを読む。部内は並列 |
| **二重読み型** | 結論を左右する重要区間 | 同じ範囲を2エージェントに独立に読ませ、食い違いを親が裁定 |

逐次リレー型は遅く、誤りが後段に伝播する。
`base.md` に前提知識を十分積めば黒板型で足りることが多いので、**まず黒板型を試す**。
