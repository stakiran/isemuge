# 恒久索引（話ダイジェスト）の仕様と作り方

原稿156万字を、**意味を保ったまま約1/6に圧縮**した索引。
1回作れば以降の全タスクで使い回す。これが無いと毎タスク156万トークン払うことになる。

- 断片の置き場: `_yokodan/knowledge/digest/agent-<N>.jsonl`
- 統合後: `_yokodan/knowledge/digest.jsonl`（1行1話・410行）
- 操作: `scripts/idx.py`

## スキーマ

1話 = 1 JSON。1行に収める（JSONL）。目安 400〜700字。

```json
{
  "id": 34,
  "chars": ["タイヨウ", "ルナ", "ユズ", "シキ"],
  "pov": "タイヨウ",
  "place": "王都・王宮",
  "when": "ナツナ暗殺の直後",
  "summary": "200〜300字。誰が何をして何がどう変わったか。あらすじではなく変化を書く。",
  "events": ["世界や関係の状態が変わった出来事だけ。変わっていないなら空配列"],
  "relations": [
    {"from": "ルナ", "to": "タイヨウ", "kind": "信頼", "dir": "+", "strength": "強",
     "note": "正体を隠していたことを詫び、以後協力すると告げる", "line": 5600}
  ],
  "emotions": [{"who": "ルナ", "what": "罪悪感", "line": 5601}],
  "reveals": ["ルナの正体が第一王女ハルナだと判明"],
  "foreshadow": ["滅亡バグの詳細は未提示のまま"],
  "quotes": [{"who": "ルナ", "text": "ごめん、黙ってた", "line": 5600}],
  "notes": "解釈に迷った点・矛盾しそうな点があればここに書く。無ければ省略"
}
```

`id` 以外の機械的事実（`vol` `file` `start` `end` `chapter` `title`）は
`idx.py` が manifest から自動で補うので、**エージェントに書かせなくてよい**（書いても上書きされる）。

### フィールドの掟

- **`relations` がこの索引の主役。** 人物間で何かが動いたら必ず1件残す。
  「変化なし」の場面は書かなくていいが、**関係が悪化した場面は絶対に落とさない**。
  好意的な記述だけ拾うと、後段の分析が単調増加になって使い物にならなくなる。
  - `dir` は `+`（近づく） / `-`（離れる） / `0`（動いたが方向は不明・両義的）
  - `strength` は `強` / `中` / `弱` の3段階のみ。**数値スコアは付けない**（理由は `rubric.md`）
  - `kind` は自由記述の短語（信頼・警戒・依存・敵意・恋愛・敬意・失望 など）
- **`quotes` は関係や人物像を決定づける台詞だけ。** 1話あたり0〜3件。多すぎると圧縮率が死ぬ。
- **`line` は必ず入れる。** 後から原文に戻れないダイジェストは信用できない。
- **`notes`（迷い）を必ず活かす。** ここに書かれた迷いを親が集約して次ラウンドの論点にする。
- 推測を書かない。本文に無いことは書かない（CLAUDE.md の「情報は常に本文から拾え」）。
  推測が有用なら `notes` に「推測:」と明示して書く。

## 構築手順

```bash
python .claude/skills/genko-yokodan/scripts/idx.py status              # 進捗確認（再開時はまずこれ）
python .claude/skills/genko-yokodan/scripts/idx.py plan --per-agent 10 # 未処理分の割り当て表
```

410話 → 10話ずつで **45エージェント**。1エージェントあたり約1,700行 / 3.4万字。

- **モデル**: `model: "sonnet"`。索引は永続資産なので品質が効く。Haikuだと関係性の機微を落とす。
- **並列度**: 一度に投げるのは10前後まで。波に分けて回す。
- **再開可能**: 各エージェントは自分の担当分を書き終えてから終了する。
  途中で落ちても `idx.py status` の欠番を `plan` で再割り当てすれば続きから再開できる。
- 全部終わったら `idx.py merge`。壊れた行が報告されたらその話だけ再走査。

### エージェントへの指示テンプレート

```
あなたは長編小説の索引を作る。担当は <file> の <start>〜<end> 行（話id <a>-<b>、<N>話分）。

1. Read("<file>", offset=<start>, limit=<lines>) で担当範囲を読む。
   これ以外の範囲は読まない。ファイル全体を読んではいけない。
2. 各話について下記スキーマのJSONを1行ずつ組み立てる。
   <ここに上のスキーマとフィールドの掟を貼る>
3. Write で `_yokodan/knowledge/digest/agent-<N>.jsonl` に書き出す。
   1行1話、<N>話ぶん。JSONとして必ずパースできる形にすること。
4. 返答は「書いたパス / 書いた話数 / 判断に迷った点（あれば箇条書き3件まで）」だけにする。
   本文や要約そのものを返答に含めてはいけない。

前提知識（作品の基本設定）:
<_yokodan/knowledge/base.md があればここに貼る。初回は空でよい>
```

**返答に本文を含めさせないこと**が要点。含めると親のコンテキストが本文で埋まり、
以降の全ターンにその分の課金が乗り続ける。

## 索引ができた後の使い方

```bash
# 関係の変遷だけを時系列で（好感度分析などはまずこれ）
python .claude/skills/genko-yokodan/scripts/idx.py timeline --pair ルナ,タイヨウ

# 特定人物が出る話のダイジェストだけ
python .claude/skills/genko-yokodan/scripts/idx.py view --chars ルナ --field summary,relations,emotions

# 全部読む（約25万字 ≒ 25万トークン。1Mウィンドウに収まる）
python .claude/skills/genko-yokodan/scripts/idx.py view

# 「両者が同席しているのに関係の記述が無い話」＝索引の取りこぼし候補
python .claude/skills/genko-yokodan/scripts/idx.py holes --pair ルナ,タイヨウ
```

`holes` は重要。索引は圧縮なので必ず取りこぼす。
**索引だけで結論を出さず、holes に挙がった話は原文で確認する。**

## 索引と一緒に育てる知識

`_yokodan/knowledge/` 配下。索引構築の副産物として親が書く。以降、全エージェントに配る。

| ファイル | 中身 | いつ更新するか |
|---|---|---|
| `base.md` | 作品の基本設定・世界観・主要人物の一行紹介 | 索引構築の第1波が終わった時点で初版。以後追記 |
| `chars.md` | 人物台帳（正体・所属・呼称の変遷・一人称） | 新キャラが索引に現れるたび |
| `timeline.md` | 年表（部単位の大きな出来事） | 索引完成後に1回まとめて |
| `glossary.md` | 用語・造語・スキル名（`vocab.py ruby` が種になる） | 随時 |

`base.md` があるとエージェントの誤読が目に見えて減る。
特に**正体・伏線・呼称の変化**は、その話だけ読んでいるエージェントには絶対に分からない。
